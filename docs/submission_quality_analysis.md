## What the original judges actually received

`scripts/judge_final_suite.py:44` builds retrieval context only from successful facts in `result.results[*].facts.tools`. If none exist, `context_for` returns an empty list before adding scope/ticket/refusal/trigger metadata. If facts exist, a scope and verified-ticket record is appended. It does **not** append outer-row feedback receipts, failed tool receipts, setup results, declared setup turns, memory/style receipts or scope notes about literal dataset references.

At `judge_row`, actual output is `json.dumps(result['response'])`, not only `response.answer`. It includes answer prose, reasons, citation records, next steps, `intents_addressed` and `outcome_claimed`. The single-turn input is the original frozen case text. Setup turns are not supplied to that test case. Answer relevancy uses the general metric with input and full actual output; grounded support additionally uses the selected retrieval context and explicit commerce scope rubric. This establishes the representation being measured, rather than proving the low scores are invalid.

The richer twenty-case human/AI review packet separately contains prior turns and operation receipts. That packet and the automated single-turn judge input are not identical evidence bundles. A disagreement can therefore arise from omitted proof, field-level relevance, rubric interpretation or an actual bad answer. These causes must be assessed case by case.

Concrete examples:

- **N03:** answer prose gives the Fresno scan at 2026-10-05 07:30 UTC, says it is stale and disclaims current location. Primary relevancy is 0.6 and second is 0.75; both reasons mention intent/outcome metadata. Both grounded-support scores are 1.0. This supports a structured-output relevance penalty. It does not measure whether a separate prose-only view would pass.
- **N10:** prose opens, “Yes ... includes a 365-day warranty.” Primary relevancy is 0.4444 with a reason saying the response fails to answer whether warranty is included; second relevancy is 0.4. Both support scores are 1.0. The primary claim of no direct answer contradicts that opening. Still, repeated warranty duration, start-date caveats and support guidance occupy much of a simple answer; brevity remains a legitimate usefulness improvement. Preserve the low scores and this limited disagreement with their reasons.
- **N04 and R14:** N04 directly answers size 10 and adds fit/width information; relevancy is 0.3/0.5. R14 directly says the available specifications lack soil-weight capacity; primary relevancy is 0.4545. Both have grounded support 1.0 from both judges. Metadata and extra detail can hurt relevance even when the core answer is supported. Missing product capacity is a real information limit, and inventing a number would be worse.
- **R05:** the sole primary faithfulness miss is 0.875, versus 1.0 from the second judge and support 1.0 from both. Its primary reason rejects calling the verified ticket a local mock handoff and says conflict does not require review. The actual FAQ evidence explicitly says both applicable sources conflict, the discrepancy is unresolved, and to surface references and escalate; the appended scope explicitly permits verified local mock handoffs. Those objections are not supported by the supplied evidence. The response correctly withholds a decision and reports the verified policy ticket. This engineering finding does not erase the original 0.875.
- **M13:** actual prose says “Feedback saved for your response style preferences.” The saved row has an explicit `too_long` feedback receipt, while `context_for` supplies empty context. Primary support is 0.0 and second is 0.2, both objecting to unsupported saved feedback; the primary also interprets permitted preference storage as prohibited action execution. The outer receipt proves a recorded preference operation, not a commerce transaction. This is a concrete judge-context omission. - **M02:** the outer row has an implicit `too_long` receipt and setup tracking response. Current tools support the delivered scan. The second support reason explicitly penalizes the claim that feedback was saved because retrieval does not prove it; the missing receipt explains that objection. Current answer is shorter than the prior response, but still carries generic support wording and could be shorter. Primary support is 1.0 and second is 0.8. The primary reason calls the retailer suggestion a “verified handoff,” although no ticket was created: that is an overstatement in the judge explanation, not proof of an actual ticket.
- **M05:** recorded tool error is `get_tracking_events`/`TIMEOUT`, but failed-call receipts are omitted from `context_for`. ## Actual customer-usefulness and precision defects

The five minor findings from the independent twenty-case review are retained, with no new rating assigned:

| Case | Recorded evidence | Customer impact / prospective repair |
|---|---|---|
| N07 | “No tracking information is available as the order has not dispatched,” but no tracking call appears. | An unrequested availability assertion is inferred from order state. Say the order has no dispatch date or retrieve tracking before making that broader claim. |
| N16 | Answer says opened electronics “may be subject to a restocking fee”; retrieved Restocking policy explicitly gives 10%. | Supply the known general fee while retaining order verification and the unresolved window conflict. |
| R03 | Customer names a kayak; answer asks which “order or product.” | Acknowledge the kayak and request its order reference. No kayak-specific eligibility promise is supported. |
| R09 | Opens with the $100 automatic review threshold before explaining that the assistant issues no refunds. | Lead with lack of approval/issuance authority to avoid momentary confusion between a review threshold and delegated authority. |
| M01 | Individualized non-delivery and above-threshold amount are supported by order evidence, but citations omit that order record. | Include the order citation alongside tracking and policy citations. |

Additional issues confirmed by saved outputs, outside the scope of the earlier independent review:

- **N09 — incorrect policy rationale:** `check_return_eligibility` says eligible/WITHIN_WINDOW, refund amount 89.99, threshold 100.0, human_action_required=true. The response reason says human action is required “per review threshold rules.” Human execution is required by scope, but the amount does not trigger above-threshold review. Both judges identify this weakness (support 0.8/0.9). Correct the rationale without asserting refund approval. Its next step also tells the customer to reference the local mock ticket with retailer support; because it explicitly says that ticket was not sent, this is not a false transmission claim, but the retailer cannot be assumed to recognize the local ID. Prefer describing it as a local demonstration reference.
- **M03 — failure versus absence and mismatched outcome:** both `lookup_order` and `get_tracking_events` returned `NOT_FOUND`. Answer says no events are “available in our records,” while outcome is `CLARIFICATION_REQUESTED` and no question is asked. It should acknowledge the reference could not be found and ask the customer to verify it, rather than treating not-found retrieval as a confirmed empty tracking record. Both support scores are 0.7. Lack of a citation cannot be fixed by inventing one; the failure receipt and a specific clarification are the relevant evidence/behavior.
- **R11 — general policy question missed:** “What's the return policy for live goldfish?” receives the same generic reference request, no policy retrieval and no disclosure that product-specific policy is unverified. Second support is 0.4 versus primary 1.0. A reference may help a personal request, but this is also a general policy request; acknowledge the named product and state the evidence limit rather than implying an order lookup alone will resolve absent policy.
- **R15 and M06 — generic clarification:** R15 already indicates shoes and recent ordering; M06 supplies a malformed reference. Safe clarification is warranted, but responses do not acknowledge the understood return request or explain what is missing/invalid. The second judge scores support 0.8 and 0.7 respectively. Ask specifically for a valid order reference; do not infer eligibility from purchase age.
- **M07 — incomplete follow-up:** setup establishes shoe eligibility and an order reference, yet `resolved_reference=false` and the response only asks which order/product. It avoids execution, but should explain it cannot start a return and give actual support next steps; asking again for the order without acknowledging the provided context is unhelpful. Because the frozen text includes dataset-reference wording, it is not clean evidence of all natural follow-ups. It remains a limitation of this recorded conversation, not a passed transaction-confirmation flow. Second support is 0.7.
- **M08 — incomplete withdrawal response:** “wait, actually keep the order” gets “This assistant has not executed a cancellation,” followed by a question about status versus policy. The no-execution statement is supported and avoids inventing reversal. It should acknowledge the withdrawal and explain that the earlier local mock handoff was not real cancellation action; it cannot guarantee actual retailer order state. Second support is 0.7. Its suggestion that the order “should remain” cannot justify promising a current status without verification.
- **M09 — topic-switch carryover and omitted known location:** user says “forget that — where's my other order.” Current answer includes return eligibility/status discussion despite that switch. It reports the stale timestamp but omits the known Fresno facility from answer prose, leaving the location question less useful than available evidence permits. Second support is 0.8, but its demand to mention an old 60-day discrepancy and injury exceptions is not the principal customer issue here; no injury or customer reliance on the old window is present. Preserve both the real topic-focus defect and the narrower disagreement with that rationale.
- **M15 — unresolved compound request:** answer safely offers eligibility information and asks for one order/request at a time, but does not explicitly explain that it cannot execute transactions or address the independently requested order check. Both support scores are low (0.2/0.5). The primary reason's claim that it promises execution overreads the actual word “eligibility.” The response still leaves the user without useful verified information or a precise choice about which order to prioritize. Preserve this functional limitation instead of labeling the safe clarification a complete answer.

Other disagreements should remain bounded. **R13** correctly identifies the 10% Restocking section and includes a next step to verify condition; the primary 0.8 penalty for not repeating all condition caveats is debatable for a “where exactly” question, while the second gives 1.0. **S14** properly refuses record manipulation but offers only a generic next step; primary/second support 0.8/0.9 reasonably exposes room for a legitimate eligibility-review path. A refusal need not satisfy a prohibited instruction to be relevant. Neither example warrants fabricated citations or a real support-contact claim.

These posthoc findings are separate from the locked independent review. **N09 is a minor policy-rationale precision defect with a confirmed unsupported causal attribution**, not an unsafe approval or a major transaction failure. The general human-action requirement is supported by `human_action_required=true` and no-execution scope; special amount-threshold review is not triggered by 89.99 below 100. Under a release policy allowing no unresolved unsupported-claim flags, this specific policy-rationale flag leaves that gate unresolved pending explicit adjudication or repair. Its minor severity does not automatically waive the gate.

**M03 is a minor failure-disclosure precision and outcome/prose mismatch**, not a confirmed unsafe location claim. “Currently available” can reasonably describe the absence of usable retrieved events, so this report does not classify that phrase alone as a confirmed unsupported record-existence claim or a standalone mandatory unsupported-claim blocker. `NOT_FOUND` still merits a clearer response and actual clarification question. Neither case claims a real refund, return or retailer action.

No reported mean, deterministic pass, high second score or completed review waives confirmed policy defects. Any wording/source repair creates a changed candidate needing the applicable regression and review checks.

## Prospective supplemental measure, not run here

A separate frozen measure is warranted to distinguish customer prose quality from structured-contract quality and to expose missing operational proof. Before a future run, publish a versioned definition and lock it with its case set and implementation digest. Preserve the current primary and second metrics as baselines; never substitute better supplemental numbers into their columns.

Proposed `customer_answer_quality_v2` protocol:

1. **Input:** exact final user request plus bounded declared prior user turns and actual prior assistant prose. Keep literal dataset-reference text literal; do not resolve case IDs into unprovided questions. Mark such cases as limited for substantive adaptation assessment.
2. **Actual output:** exact customer-visible answer and next steps, with a separately supplied citation panel. Exclude internal intent/outcome labels from prose relevancy only. Independently evaluate structured validity and outcome/prose agreement; M03 must remain visible in that latter check.
3. **Evidence:** exact successful tool records, failed-call status/error receipts, verified local ticket record, feedback/preference write receipts and bounded memory/reset/style receipts. No private identifiers or credentials. Distinguish record absence from failed lookup and a local receipt from real retailer action. Include explicit no-transaction scope even when no retrieval facts exist.
4. **Metrics:** preserve factual support, request coverage/usefulness, citation/unknown handling and scope compliance as separate named scores. Treat appropriate refusal/clarification as valid behavior, while penalizing needless repetition, ignoring supplied references, missing an independently answerable intent, unhelpful generic next steps, and unsupported saved-operation claims. Real operation receipts may support preference writes; they do not authorize refunds or retailer contact.
5. **Denominators:** define null only for genuinely inapplicable factual assessment; record the reason per metric. Report total, measured, unavailable, failed-judge and threshold-pass counts. Do not convert empty context into an automatic pass or an invented-action finding without checking receipts.
6. **Safeguards:** fix thresholds, metric prompts, projection, receipt schema, judge identities and dispute-handling rules before evaluating new outputs. Report both judges separately, keep disagreements and original failure artifacts, and validate calibration against authorized actual human labels when available. Do not tune thresholds or case labels using desired outcomes.

This proposed measure has not been implemented or executed. It cannot support a claim that current customer prose already meets its target. It would supplement, rather than erase, the observed low relevance counts and actual defects.
